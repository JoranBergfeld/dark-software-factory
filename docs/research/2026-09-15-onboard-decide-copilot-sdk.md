# Copilot SDK authentication and GitHub App compatibility

Research date: **2026-09-15**. Resolves [#199](https://github.com/JoranBergfeld/dark-software-factory/issues/199), research for map [#189](https://github.com/JoranBergfeld/dark-software-factory/issues/189) and the human decision in [#191](https://github.com/JoranBergfeld/dark-software-factory/issues/191).

## Answer

**Yes, conditionally: current first-party SDK documentation explicitly supports GitHub App installation tokens for Copilot inference, not merely for repository tools.** The supported server-to-server route is the runtime's `COPILOT_GITHUB_TOKEN` environment variable, **not** `.NET CopilotClientOptions.GitHubToken` or the session token option. It requires `copilot_requests: write`, an enabled installation/billing account, and currently **All repositories access on the App installation**, even though the minted inference token specifies a repository ID. Tokens expire after one hour; documented rotation restarts the runtime. This is a material prerequisite, not permission to broaden the DSF App automatically. [S1]

**An App-signed JWT is not a documented Copilot inference credential.** It authenticates the owner broker to GitHub's App-management/token-minting API. Do not send the signing key or App JWT to a factory or treat a constructor's `string` parameter as evidence of service support. A GitHub-issued installation token whose new format contains `JWT` is still an installation token, not that App-signed JWT. [S1][G2][G3]

**A separate viable .NET route is Azure model BYOK with managed identity, plus broker-issued DSF App tokens only inside custom GitHub tools.** This bypasses Copilot service authentication/subscription for model inference. Current .NET source and tests implement per-request `BearerTokenProvider`; that particular API remains **experimental**, despite SDK general availability. This is not a Node-only workaround and does not require a persisted human GitHub credential. Actual DSF account eligibility, deployment compatibility and long-running behavior remain unverified: no credentials, installation changes, paid sessions or live token experiments were performed. [S2][S3][S4][S5]

**Source inconsistencies matter.** The current SDK README still says BYOK is key-only and managed identity is unsupported, while its dedicated Azure guide, released .NET callback implementation and tests say otherwise. The same README gives an overbroad subscription requirement; the dedicated authentication guide explicitly documents organization-billed, no-user-subscription server-to-server authentication. The general CLI token table omits installation tokens, while both the specific SDK server-to-server guide and official Actions docs cover them. Report the specific supported route and experimental qualifier, rather than repeating either generic statement as an absolute. [S1][S2][S3][S4][S5][S7][G1][G4]

Here, **documented** means first-party support is stated; **experimental** means implemented but explicitly unstable; **unsupported route** means outside the documented contract (not a claim of observed HTTP rejection); **unverified** means sources do not establish the particular deployment/account/runtime outcome.

## Three independent authorization boundaries

| Boundary | Credential / authority | Does not confer |
| --- | --- | --- |
| Copilot service and session inference | Supported GitHub user credential with entitlement, or the documented installation-inference route with account policy/billing | Azure access; DSF approval to modify repositories; automatic eligibility of an existing App |
| BYOK model inference | Azure managed-identity Entra bearer token, or separately approved provider key | GitHub identity, repository permissions, a Copilot seat, or cloud-agent assignment |
| Custom GitHub operations | Owner-broker-issued installation token narrowed to product repository and permitted operations | Copilot inference unless separately minted for its requirements; permission to choose the issue-edit policy |

This separation follows the SDK's separate `Provider`, user-authentication and host-executed custom-tool surfaces, plus GitHub's token scoping rules. A factory can therefore act as the DSF App on GitHub while its models authenticate as Azure workloads. Conversely, App-authenticated inference does not mean every tool must receive that inference token. [S1][S2][S8][G2]

### Copilot credential matrix

| Credential | Copilot inference status | Identity, entitlement and operational limit |
| --- | --- | --- |
| GitHub App installation token (`ghs_`, including the new stateless format) | **Documented, conditional** through `COPILOT_GITHUB_TOKEN` in the runtime environment | App installation identity. App needs **Copilot Requests: Read & write**; token request includes `repository_ids` and `permissions.copilot_requests = "write"`; installation currently needs **All repositories** access. Organization must be enabled. One-hour lifetime. [S1][G2][G3] |
| Same installation token in SDK `GitHubToken` | **Explicitly unsupported route** | First-party warning: explicit token option is for user tokens. The .NET client uses a distinct `--auth-token-env COPILOT_SDK_AUTH_TOKEN` path, not the generic runtime environment path. [S1][S9] |
| App-signed JWT | **No documented inference support** | Used by the owner broker to mint installation tokens/manage the App; no inference support claim found. Actual Copilot rejection was not tested. [G2] |
| GitHub App user token (`ghu_`) | **Documented user route** | OAuth user authorization; acts on behalf of that user, not solely as the installation. User access and App permissions intersect. Copilot user entitlement remains relevant; this is not an unattended App-identity escape hatch. [S2][G1][G5] |
| OAuth App/browser/device token (`gho_`) | **Documented user route** | User-backed Copilot access, consent and token lifecycle. Not a factory workload identity. [S2][G1] |
| Fine-grained PAT (`github_pat_`) | **Documented user route** | Must be personal-account-owned with **Copilot Requests account permission**, distinct from the App's repository permission. Uses user seat entitlements; rejected by the current no-human-token factory constraint. [G1][G4] |
| Classic PAT (`ghp_`) | **Explicitly unsupported** | Official CLI token table and SDK auth guide say no. [S2][G1] |
| Azure managed-identity token | **Not Copilot service authentication; documented BYOK route** | Audience is the model provider, not GitHub. [S3][M2] |

**Entitlements and billing:** the SDK explicitly describes organization-attributed server-to-server use as requiring no user subscription but requiring organization policy. Its guide bills the account owning the installation, including user-account attribution. Official Actions documentation independently distinguishes personal-owner seat billing from direct organization billing and says the working organization need not itself issue Copilot licenses if the policy is enabled. However, Actions' built-in `GITHUB_TOKEN` is not a credential an Azure Container App automatically receives. Do not generalize Actions eligibility to every custom-App installation. The guide's outside-Actions recipe is organization-focused; full personal-installation eligibility and this owner's settings are **unverified**. Exact allowed models and budgets also remain account-dependent. [S1][S2][G4]

**Rotation:** for installation inference, mint a replacement through the owner broker before expiry and restart the SDK child runtime with its new environment; existing/FFI runtimes likewise need restart. Do not infer hot installation-token refresh support from the separate experimental session `GitHubTokenProvider`: its documented path resolves a stable account identity and is not offered as an exception to the installation-token warning. Restart/resume behavior across long council work is a later acceptance obligation, not proven here. [S1][S10]

**App reuse implication:** human approval to reuse the broader owner App is not evidence that its installation already meets `All repositories`, `copilot_requests` and billing requirements, nor approval to add them. Repository-restricting each token reduces its usable scope but does not erase that broader installation prerequisite. If it is unacceptable or unavailable, BYOK does not need this Copilot App permission. [S1][G2]

## Azure-hosted model BYOK in .NET

The source-backed shape is `.NET CopilotClient` plus a session's **singular `Provider`**, an explicit deployment `Model`, and an Azure Identity-backed `BearerTokenProvider`. In the dedicated guide, `Type = "openai"`, `BaseUrl = https://<resource>.openai.azure.com/openai/v1/`, and the callback acquires the `https://ai.azure.com/.default` audience. Microsoft's managed-identity guidance corroborates the endpoint, audience and **Cognitive Services OpenAI User** resource role for Azure OpenAI inference. No model key or GitHub user token is intrinsically needed. Add `Azure.Identity` for the credential implementation; the guide's .NET prerequisites list only `Azure.Core` despite importing `Azure.Identity`. [S3][M2]

Important limits:

| Concern | Established finding / consequence |
| --- | --- |
| SDK and runtime | SDK is now generally available, but `.NET ProviderConfig.BearerTokenProvider` has `[Experimental(Diagnostics.Experimental)]` (`GHCP001`). Pin compatible SDK/runtime versions and explicitly acknowledge the experimental surface. Released `v1.0.13` already contains it; the package targets `net8.0`, `net10.0` and `netstandard2.0`. .NET bundles the CLI/runtime; this remains a native runtime dependency, not a pure managed single model HTTP call. [S4][S6][S7] |
| Refresh | Runtime requests a token through session-scoped `providerToken.getToken` before outbound provider requests. Callback takes precedence over `ApiKey`/static `BearerToken`. Reuse a specific `ManagedIdentityCredential` and call `GetTokenAsync` when asked; the identity library can cache/refresh, rather than minting a new Entra token for every model request. Static `BearerToken` is **not automatically refreshed**; documented recovery is a fresh session/token. [S4][S5][S11][M1] |
| Proof level | Released upstream .NET tests verify outgoing authorization, repeated acquisition and per-provider dispatch using intercepted OpenAI-compatible requests. They return synthetic errors rather than complete live Azure inference. This proves wiring, not DSF RBAC, network reachability, provider acceptance or uninterrupted multi-hour operation. [S5] |
| Callback limitations | Signature is `Func<ProviderTokenArgs, Task<string>>`; arguments carry provider name/session ID, not a `TokenCredential`, scope, expiry or cancellation token. The application selects the correct audience and imposes acquisition deadlines/error handling. A missing registered callback causes an explicit error; source dispatch does not substitute another identity. [S4][S12] |
| Production identity | Prefer an explicit workload-specific `ManagedIdentityCredential`, not an unconstrained developer-friendly credential chain. `UseLoggedInUser = false` controls GitHub fallback, **not** Azure Identity fallback. Microsoft recommends deterministic credentials and reuse; its constrained `DefaultAzureCredential` resilient-mode guidance requires Azure.Identity 1.16.0+. [S9][M1] |
| Endpoint/protocol | `openai` expects the full compatible API base; `azure` expects the resource root and constructs Azure paths. `Azure.ApiVersion` selects a versioned deployment route; absent version uses v1. `WireApi = "completions"` is the compatibility path; use `"responses"` only where the selected deployment supports it. `anthropic` uses Messages, not a universal OpenAI adapter. A generic callback does not prove every Azure-hosted provider accepts Entra tokens. [S11] |
| Model selection | BYOK requires an explicit model/deployment and exposes only provider-supported models. Model listing may need application-supplied metadata; it is not deployment verification. Provider rate limits/billing apply. Do not substitute a Copilot catalog model with a similar name for an approved Azure deployment. [S11] |
| Multiple providers | Experimental `Providers`/`Models` registry is **additive to Copilot authentication**, unlike singular `Provider`, and cannot be combined with it. Do not assume adding three registry entries creates a GitHub-auth-free jury. Separate singular-provider sessions or existing direct model clients avoid that assumption. [S13] |

The managed-identity sample's `"responses"`/GPT example is not evidence that the same wire format works for all three juror families. DSF's current jury client specifically uses v1 **chat completions**, the `ai.azure.com` audience, and checks the returned model family; its synthesis client instead uses a versioned Azure OpenAI route and `cognitiveservices.azure.com` audience. Preserve endpoint/audience contracts; do not mechanically transplant one token scope to every existing call. [D2][D3]

## GitHub custom tools and preventing unintended authority

**Feasible composition:** a .NET tool delegate obtains a token from the owner-controlled broker and calls the GitHub API independently of session/model authentication. `CopilotTool.DefineTool` builds an `AIFunction`; the SDK invokes it in the application. The broker can retain all signing material and mint a product-repository token with an explicit permission subset and expiry. GitHub permits narrowing installation tokens to selected repositories and permissions, never beyond the installation's grant. Omitting either subset inherits broader access; this is inappropriate for the disclosed broad owner App. Enterprise-level installations have a separate no-downscoping exception and must not be confused with ordinary repository installations. [S8][G2]

**Recommended constraints, not a choice of issue policy:**

1. Authenticate the factory workload to the broker; derive the permitted installation/repository/operation from owner-controlled policy, not arbitrary model-supplied owner, repository, URL or permission strings. Validate inputs again in the custom-tool implementation. Return domain data, never a token, signing material or credential-bearing error.
2. Separate **inference-purpose** tokens, if option A below is chosen, from **GitHub-operation** tokens. Tool tokens need only the human-approved repository operations, not `copilot_requests`; an inference token need not carry contents, PR or Issues write permissions.
3. Keep tool tokens in host memory with bounded caching/renewal, not prompts, SDK session configuration, child-process environments, shell arguments or persisted human credential stores. Audit operation/repository/result/expiry metadata without secrets.
4. Preserve no standing contents/PR write authority. Operator preview/publication of intent PRs continues using the operator's existing `gh` login, outside the factory. Issue-edit scope remains explicitly undecided; expose no generic write capability as a way around that decision.

These recommendations apply the actual host-tool execution and GitHub token-narrowing boundaries, rather than assuming model instructions enforce authorization. App permissions are coarser than an application policy such as "edit only approved issue fields"; the host/broker must enforce that narrower policy once the human defines it. [S8][G2]

### Default tools, callbacks and ambient behavior

The default client mode is `CopilotCli`, exposing first-party CLI tools, not a read-only model client. Upstream tests explicitly check removal of shell, editing, search and web tools in constrained mode. **Do not copy examples using `PermissionHandler.ApproveAll`.** Availability and permission decisions are separate controls. [S7][S14][S15]

For a later constrained Decide integration, the source supports:

| Surface | Source-backed control and caveat |
| --- | --- |
| Shell/filesystem/network tools | Start with `Mode = CopilotClientMode.Empty`, explicit isolated `BaseDirectory` or `SessionFs`, and an explicit `AvailableTools` list. Use `[]` for no tools, or exact source-qualified entries such as `custom:<approved-name>`; no `builtin:*`/`mcp:*`/`custom:*` wildcard. `ExcludedTools` is an additional denylist; released .NET resolves exclusions first. `ToolSet` classifies tools by registration source, not spoofable naming alone. [S14][S16] |
| GitHub MCP | Disable the configured built-in GitHub server by exact name (`DisabledMcpServers = ["github"]` in the upstream example), omit other MCP registrations, and turn `EnableConfigDiscovery` off. An empty `McpServers` dictionary alone is not evidence ambient configured servers disappear. Disable applies at create/cold resume, not to an already-running resident server. Custom host API tools do not require GitHub MCP. [S17][S18] |
| Permission callback | Set `OnPermissionRequest` explicitly to reject everything outside the approved operation set. `Reject` denies; `NoResult` is **not denial**, but yields to another connected client. Missing callback is not a universal sandbox: one code path returns `UserNotAvailable`, while event delivery can defer to another client. `SkipPermission` on a custom tool bypasses prompting; do not use it to bypass governance. Host tools still require their own authorization. [S8][S15][S19] |
| Instructions, hooks, agents, schedules | Empty mode defaults off file hooks, host git operations, skills, shared session store, memory and embedding retrieval; it strips environment context and disables further ambient features. Set configuration discovery off explicitly, and do not provide plugin/instruction/skill/custom-agent directories. Explicit plugins can load even when discovery is off. Do not expose spawning/fleet/scheduling tools or accept `BuiltInTools.Isolated` wholesale: that curated set still includes agent dispatch. [S14][S16][S18] |
| Ambient credentials | Set `UseLoggedInUser = false`, provide a minimal child environment and isolated home, remove inherited `GH_TOKEN`, `GITHUB_TOKEN`, direct Copilot API overrides and unrelated provider secrets. Only include `COPILOT_GITHUB_TOKEN` when deliberately selecting installation inference. Empty mode disables the shared OS keychain but can use file storage in `COPILOT_HOME`; it does **not** mean "credentials can never persist." Do not mount the operator's `gh`/Copilot/Azure login stores. [S9][G1] |
| Actual containment | Tool filters and callbacks are application controls, not an OS/network sandbox or a restriction on arbitrary custom-tool code. Use the dedicated worker, workload-separated identity, restricted mounts and egress, broker enforcement and minimal token permissions as independent boundaries. No access to the existing application's working tree or deployment is needed merely to host the SDK. [S8][S14][G2] |

If using installation inference, the short-lived inference token necessarily reaches the runtime environment. Thus removing shell/environment-reading/extension capabilities matters even when that token has no GitHub content-write permission: it can still authorize billed inference. A stdio child runtime isolates environment/lifecycle more clearly than FFI, where the environment is shared with the host, or a shared URI runtime, whose authentication must be configured on that external process. [S1][S9]

### Side effects beyond repository writes

SDK sessions execute an agent loop: one send can cause multiple model requests and tool calls. Automatic context compaction and session workspace persistence are enabled by default; large tool output can spill to files. Disposing a .NET session disconnects it but does not delete persisted state. Budget/deadline enforcement, finite task boundaries, data retention and idempotency remain host responsibilities; an SDK "idle" event is not a DSF checkpoint, approval or jury verdict. [S20][S21]

BYOK is **not automatically offline or telemetry-free**. Official CLI docs say unauthenticated BYOK can still send telemetry. .NET separately disables internal session telemetry for singular BYOK, while OpenTelemetry export is independently configured; these are different telemetry channels. Keep only approved ordinary metadata in the dedicated factory Insights/Logs path, do not enable message-content capture, and verify runtime egress/retention before deployment. CLI `COPILOT_OFFLINE=true` is documented to suppress GitHub contact and telemetry, but it is not a sandbox for host-executed custom GitHub tools and must not be assumed to preserve every SDK feature without later validation. No additional telemetry destination is approved by this research. [G1][S13][S22]

## Options for the human, without changing the council

| Option | What is feasible | Decision / acceptance still needed |
| --- | --- | --- |
| **A. Copilot inference as DSF App installation** | Broker mints dedicated inference token; .NET stdio child receives it through `COPILOT_GITHUB_TOKEN`, disables user fallback, uses empty-mode tool restrictions. GitHub tools use separately narrowed broker tokens. [S1][S14] | Existing installation eligibility, **All repositories** prerequisite, Copilot repository permission, owner billing/model policy, hourly runtime restart and recovery. This changes model service/billing; it does not automatically use the approved Azure deployments. |
| **B. Azure BYOK + managed identity; DSF App only for GitHub tools** | .NET singular `Provider` plus experimental bearer callback; existing approved Azure endpoint/deployment; separate broker-authorized GitHub tools. No Copilot user token or Copilot App inference permission required. [S3][S4][S8] | Accept experimental callback/version-pinning risk; verify real provider/protocol support, refresh, finite sessions, denied tools and ordinary telemetry. Best alignment with the already-approved Azure-model/identity boundaries, if the SDK's agent loop is actually wanted. |
| **C. Keep direct .NET model clients; add no SDK** | Existing Entra-authenticated synthesis and three-family jury clients remain; the proposed broker supplies GitHub operations independently. [D1][D2][D3] | Suitable baseline if no agent-loop requirement justifies SDK/runtime complexity or experimental surface. This is an option, not a decision made here. |

User OAuth, App-user tokens and PATs are technically different supported user routes, **not compatible substitutes under the current no-human-token factory constraint**. A separate model gateway could manage provider authentication, but is additional infrastructure, unnecessary merely to obtain today's .NET callback support, and not approved here.

**Council/jury invariants stay intact.** DSF requires exactly three independently configured GPT, DeepSeek and Grok families, distinct names and endpoint/deployment targets; the runtime checks response model family. S3 synthesis, the deterministic recommendation, separate validation jury, grounding/dedup gates, maturity escalation, audited errors and filing policy remain DSF responsibilities. Do not replace the jury with three SDK personas on one model, rely on automatic model selection, or treat the SDK's agent loop as a council verdict. Preserve the approved factory synthesis/embedding deployments; SDK internal embedding retrieval is not that embedding contract. SDK service authentication also does not assign GitHub Cloud Agent work: `/delegate` is a distinct GitHub-hosted capability, unnecessary here. [D1][D2][D4][S18][G1]

**Planning boundary:** all options preserve the existing application's repository and Azure deployment. They operate only within the approved dedicated council worker/source agents, product App Configuration/Key Vault/Cosmos, factory-only Insights/Logs, separated workload identities, prepared owner control plane and approved shared model providers. No App changes, new standing contents/PR write permission, issue-edit policy, replacement jury or wider telemetry approval is inferred.

**Remaining uncertainty is bounded:** this research settles documented feasibility, not this owner's enablement or an operational rollout. A later separately authorized acceptance exercise would need to establish account policy/billing, chosen SDK/runtime/provider compatibility, token-expiry recovery, exact tool denial and session-resume behavior, approved telemetry, and preservation of three-family model identity. No such experiment is authorized or claimed here. No issue other than #199 is updated by this research worker.
